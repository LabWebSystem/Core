# LWS 機能テストルール

## 目的

- LWSの機能を、決めた動作どおりに保つ。
- 変更前に、期待する動作をテストで固定する。
- テストは、対象に最も近い場所へ置く。
- テストは`mise`から実行する。

## 仕様の正本

仕様が食い違うときは、次の順で優先する。

1. 機能定義書
2. OpenAPI契約
3. Infrastructure・Backend仕様書
4. この文書

- 仕様を変えるときは、実装とテストを同時に更新する。
- 仕様、実装、テスト、MemADRの内容を一致させる。

## テストの種類

### Infrastructureテスト

- Compose、DNS、Reverse Proxy、network、volumeを確認する。
- Docker resourceの所有権と削除範囲を確認する。
- 本物のDockerが必要な場合は、専用のテスト環境を使う。
- 開発環境や無関係なDocker resourceを使わない。

主な場所とコマンド:

- `scripts/test-infrastructure.sh`
- `mise run test infrastructure`

### Backendテスト

- 入力検証、DB、HTTP、Operation、Runtime、Docker連携を確認する。
- 外部コマンドは、必要な範囲でFakeに置き換える。
- Dockerを実際に動かす必要がないテストでは、Dockerを起動しない。
- HTTP APIの外部契約は、HTTPテストで確認する。

主な場所とコマンド:

- `backend/`
- `cmd/`
- `scripts/`
- `mise run test <target>`

### Frontendテスト

- Dashboardの表示、入力、選択、状態遷移を確認する。
- APIをモックして、画面の状態管理を高速に確認する。
- 操作中のボタン、エラー表示、再取得後の選択状態を確認する。
- BackendやDockerを必要としない画面テストで、実環境を起動しない。

主な場所とコマンド:

- `dashboard/src/**/*.test.*`
- `npm --prefix dashboard test`
- `mise run test-dashboard`

### E2Eテスト

- ブラウザからLWS全体を操作する。
- Dashboard、Backend、Infrastructure、登録アプリの境界を確認する。
- 小さな内部変更の確認には使わない。
- 実環境E2Eは、専用のCompose project、network、volumeを使う。
- テスト終了時に、テスト用resourceだけを削除する。

主な場所とコマンド:

- `dashboard/e2e/`
- `qa/suites/`
- `mise run test-dashboard-e2e`
- `mise run qa*`

## テストを追加する条件

### Infrastructure・Frontend・Backend

次の場合は、実装より先にテストを追加する。

- 小さな機能を追加するとき。
- バグを修正するとき。
- 品質、安全性、互換性を確認するとき。

実装の手順は次のとおりとする。

1. 期待する動作またはバグの再現条件をテストに書く。
2. 実装前にテストが失敗することを確認する。
3. テストを満たすように実装する。
4. 関連する既存テストを実行する。
5. 変更範囲に応じた品質ゲートを実行する。

バグを修正するときは、再現テストを回帰テストとして残す。

### E2E

次の場合にE2Eテストを作成または更新する。

- LWS全体の安定性を評価するとき。
- LWS全体の性能や効率を評価するとき。
- 複数コンポーネントにまたがる大きな機能を追加するとき。
- Dashboard、Backend、Dockerなどの境界を確認するとき。

小さなFrontend、Backend、Infrastructureの変更は、まず各層のテストで確認する。複数層の不具合だけをE2Eへ追加する。

## テスト項目の書き方

各テスト項目には、次を含める。

- 前提条件
- 利用者またはテストが行う操作
- 成功したときの結果
- 失敗したときの結果
- 残すresource
- 削除するresource
- 再実行したときの結果

次の確認を必要な範囲で行う。

- Operationが完了したか。
- エラーが利用者へ表示されたか。
- API、CLI、DNS、公開URLから利用できるか。
- source、runtime、named volumeが正しく残るか消えるか。
- secretやホストのpathを表示・ログ出力しないか。
- 決まった秒数ではなく、healthcheckやOperationの状態を待っているか。

## 機能テストID

- Fixture基盤は`TF-V1-xxx`とする。
- 受け入れテストは`FT-V1-xxx`とする。
- Robotのテスト名には対応するIDを含める。
- CoreのテストはGoの`Test...`または対象別Shellテストとする。
- 未実装の受け入れテストには`planned`タグを付ける。
- `planned`のテストを、別の内部テストで成功扱いにしない。

Shellテストが項目を出力するときは、次の形式を使う。

```text
TEST_ITEM|<テスト項目ID>|<成功または失敗>|<概要>
```

## テスト環境の安全性

- テストは、対象を識別できるCompose project、label、network、volumeを使う。
- LWSの所有を確認できないDocker resourceを削除しない。
- 通常のテストで`docker system prune`や`docker volume prune`を使わない。
- 実行前から存在するimage、volume、networkを無断で削除しない。
- 失敗しても専用テスト環境を片付ける。
- 開発中のLWSや起動済みLWSを、隔離テストの状態として共有しない。

## 品質ゲート

品質ゲートは`mise run verify`とする。

- `mise run verify`または`mise run verify fast`: 静的検査、Core高速テスト、SDK、Dashboardを確認する。
- `mise run verify qa`: fastに加えて、Core統合テスト、自己完結QA、隔離lifecycle QAを確認する。
- `mise run verify release`: qaに加えて、`.deb`と`.rpm`を生成する。

- 変更した層のテストを先に実行する。
- 機能追加やバグ修正では、関連する回帰テストを品質ゲートに含める。
- テスト結果とログは`test/result/`へ保存する。
- テストを追加しただけで、品質ゲートへの追加を省略しない。

## 完了条件

機能や修正は、次を満たしてから完了とする。

- 成功する動作をテストしている。
- 主な失敗動作をテストしている。
- バグ修正には再現テストがある。
- 必要なInfrastructure、Frontend、Backendテストが成功している。
- 必要なE2Eテストが成功している。
- 対応する`mise`品質ゲートが成功している。
- OpenAPI生成物に意図しない差分がない。
- テスト後にLWS外のresourceが変更されていない。
