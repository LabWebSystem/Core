# LWS 機能テストルール

## 1. 目的

本書は、LWSの正式リリース機能を利用者のワークフロー単位で検証するためのルールを定める。

機能テストは、実装内部の都合ではなく、利用者が行う操作と観測できる結果を検証する。既存のBackend・Infrastructureの仕様書および`docs/relese/v1/機能定義書v1.md`と矛盾する場合は、機能定義書、API契約、Infrastructure仕様書の順に確認し、重複した独自仕様を作らない。

## 2. テスト先行の進め方

新しい機能は、次の順序で実装する。

1. 機能定義書に利用者の前提、操作、成功結果、失敗時の保持条件を記載する。
2. 機能テスト項目を追加する。
3. 未実装の状態でテストを実行し、期待どおりに失敗することを確認する（RED）。
4. テストを通す最小の実装を追加する（GREEN）。
5. 実装の整理を行い、テストが継続して成功することを確認する（REFACTOR）。

REDの失敗は、未実装または仕様不一致によるアサーション失敗でなければならない。Docker daemon停止、ポート競合、外部ネットワーク障害、fixture不足など、テスト環境の不備による失敗をREDとして扱わない。

未実装テストを常時失敗する状態でmainへ残してはならない。作業中は対象テストと未実装理由を作業ブランチで管理し、実装完了時にGREENへする。

## 3. テスト階層

機能テストは次の階層で構成する。

```text
機能ワークフロー
  ├─ HTTP / CLI契約
  ├─ Backend component・DB・Operation
  ├─ Git・Docker・Compose境界
  ├─ 生成設定・状態遷移
  └─ 実Compose統合
```

### 3.1 機能ワークフロー

利用者の一連の操作を検証する。成功経路だけでなく、途中の失敗、再試行、復旧後の状態を含める。

各ワークフローでは、最低限次を確認する。

- 操作受付と最終状態
- SQLiteの正本状態
- Dockerの実状態
- DNS・Reverse Proxyの公開状態
- source、runtime、named volumeの保持または削除
- Operationの状態とエラー
- secret、ホスト絶対path、内部情報の非表示
- 再実行または復旧が可能か

### 3.2 境界・componentテスト

機能ワークフローを構成する検証、migration、worker、source切替、生成設定、Docker argvなどを検証する。外部コマンドはfakeを使用し、引数、順序、timeout、呼び出し禁止条件を確認する。

### 3.3 実Compose統合テスト

実Dockerで確認するのは、代表的な公開経路、名前解決、network分離、設定reload、resource所有範囲など、fakeでは保証できない内容に限定する。専用Compose project名と一時ディレクトリを使い、終了時はLWS所有を確認したresourceだけを削除する。

## 4. テストの記述ルール

テスト項目には一意なIDを付ける。v1の機能テストは`FT-V1-xxx`、componentテストは既存の`U-*`、`H-*`、`D-*`、統合テストは`I-*`を使用する。

各機能テスト項目は、次の形式で記述する。

```text
ID:
対象機能:
前提:
操作:
成功時の期待結果:
失敗時の期待結果:
保持・削除条件:
テストレベル:
実行target:
```

テスト名には機能IDを含める。テストの待機は固定sleepではなく、healthcheck、状態ポーリング、期限付きcontextを使う。外部サービスの実通信に依存するテストは通常CIへ入れず、再現可能なfakeまたはfixtureへ置き換える。

Shellで実装した機能テストは、結果を次の機械可読形式で標準出力へ出力する。

```text
TEST_ITEM|<テスト項目ID>|<成功または失敗>|<概要>
```

`test.sh`はこの出力を日次結果へ集計する。テスト項目の実行結果を出力しないテストは、項目別結果では未出力として扱う。

## 5. 失敗と原子性のルール

処理途中で失敗した場合は、機能定義書に記載した保持条件を検証する。特に次を必須とする。

- 新sourceの検証失敗で旧sourceを失わない
- Docker起動・再構成失敗で既存の公開経路を不要に壊さない
- Caddyfile、hosts、overrideを部分更新しない
- DBの正本更新前に派生物だけを確定しない
- unregister失敗時に再試行可能な状態を残す
- purgeで所有確認できないresourceを削除しない
- LWS外のcontainer、network、volumeを操作しない

成功結果だけでなく、失敗後に再実行した結果も検証する。

## 6. 合格基準

v1機能を完了とする条件は次のとおりとする。

- 対応する機能ワークフローがGREENである
- 定義した主要失敗経路がGREENである
- 対応するcomponent・契約テストがGREENである
- 必要な実Compose統合テストがGREENである
- `mise run verify qa`が成功する
- OpenAPI生成物に差分がない
- テストをskip、無条件pass、環境依存の常時許容で回避していない
- テスト実行後にLWS外のDocker resourceを残していない

次の状態は合格とみなさない。

- 期待結果をログ出力するだけで検証していない
- Operationの完了を待たずに成功扱いする
- HTTP成功だけを確認し、DB・Docker・公開経路を確認しない
- 実装と同じ関数を呼び出して結果を比較するだけのテスト
- 未実装テストを無期限に失敗したまま残す

## 7. 実行入口

通常の開発では、対象を絞ったテスト、全テスト、lint、packageの順に実行する。

```sh
mise run test fixtures
mise run test backend
mise run test backend-http
mise run test backend-docker
mise run test infrastructure
mise run test architecture
mise run verify          # 高速な通常開発用
mise run verify qa       # 実Docker・Robot QAを含む
mise run verify release  # リリース用
```

機能テスト項目のID、対応する実装、テストファイル、実行targetを追跡可能にする。項目を削除または対象外へ変更する場合は、機能定義書とテスト項目書を同時に更新する。

`mise run test`の実行結果は、成功・失敗にかかわらず`test/result/YYYY-MM-DD-test-result.md`へ生成する。同じ日に複数回実行した場合は、その日の最新結果で上書きする。テスト結果には対象、終了status、実行時刻、標準出力・標準エラーのログを記録する。

`mise run verify`は端末には`VERIFY_ITEM`形式の統一要約だけを出力し、全検証の結果と生ログを`test/result/YYYY-MM-DD-verify-result.md`へ保存する。Robot FrameworkのHTML詳細結果は、この集約レポートからリンクする補助成果物とする。

## 8. 機能受け入れテスト

利用者が観測できるCLI、API、DNS、HTTP、Docker、パッケージの操作をまたぐ機能受け入れテストは、LWS本体と分離した`qa/`でRobot Frameworkにより管理する。機能シナリオの正本は`qa/suites/`の`.robot`ファイルとし、Backendや`cmd/`へ機能テスト用コードを追加しない。

```sh
mise run qa
mise run qa-current
mise run qa-live
mise run qa-lifecycle
mise run qa-docs
```

`mise run qa`の結果は`test/result/robot/`へ出力し、未実装項目を含む現在の進捗を確認する。通常QAは外部起動済みLWSを必要とする`live`タグを除外する。Robotの全テストが完遂した場合は、FAIL項目が残っていても`--nostatusrc`により`mise`自体は成功する。`mise run qa-current`は`planned`と、専用のhost portを必要とする`isolated`タグを除外した自己完結受け入れテストのCI用入口で、結果を`test/result/robot-current/`へ出力する。`mise run qa-live`は起動済みLWSの公開経路へ接続する`live`タグのテストを実行し、結果を`test/result/robot-live/`へ出力する。APIへ接続できない場合はSKIPせずFAILとして記録する。`mise run qa-lifecycle`は一時Compose環境をbuildしてLWS本体の起動・停止・再構成を検証し、結果を`test/result/robot-lifecycle/`へ出力する。インストールテストは一時Dockerコンテナ内でrootとしてinstall scriptを実行し、コンテナを自動削除する。機能テストの静的HTML・JSONドキュメントは`docs/generated/`へ出力する。未実装の受け入れシナリオは`planned`タグで管理し、Go・Shell・SDKの内部テストをRobotから再実行してGREENにしてはいけない。SKIPは必須ポート占有など、本当にテストを実行できない場合に限る。
