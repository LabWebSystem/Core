# LWS 機能テストルール

## 目的と正本

この文書は、LWSが利用者に見える形で正しく動くことを確認するための説明です。

機能の正しい動きは、次の順で確認します。

1. 対応する機能定義書
2. OpenAPI契約
3. Infrastructure・Backend仕様
4. 本書

内容が食い違うときは、上の資料を優先します。仕様を変えるときは、テスト項目も一緒に直します。

## 基本方針

- 利用者が操作して確かめることは、QAで確認します。
- プログラムの中だけで確かめられることは、そのプログラムのテストで確認します。
- 本物のDockerが必要なことは、分けたテスト環境で確認します。
- すべてのテストは`mise`から実行します。結果は一つのレポートにまとめます。

通常の開発では、まず次を実行する。

```sh
mise run verify          # 高速な開発・通常CI用
mise run verify qa       # 実Docker・Robot QAを含む統合確認
mise run verify release  # リリース前の最終確認
```

## テストの責務

テストごとに、確認する内容を分けます。

| 種類 | 確認すること | 主な場所 | 実行コマンド |
|---|---|---|---|
| Core | 入力チェック、状態の変化、source・Dockerのつなぎ目、CLI、パッケージ | `backend/`、`cmd/`、`scripts/` | `mise run test <target>` |
| 実Docker統合 | DNS、Caddy、networkの分離、LWSのDocker resource | `scripts/test-infrastructure.sh` | `mise run test infrastructure` |
| QA | CLI、API、公開URLを使う一連の操作 | `qa/suites/` | `mise run qa*` |
| 構造検査 | `mise`、Workflow、QAの役割分担 | `scripts/test-quality-architecture.sh` | `mise run test architecture` |

Robot Frameworkは、利用者が行う操作を確認します。SQLiteの中身、Dockerコマンドの引数、生成ファイルの細かい内容は、Coreまたは実Docker統合テストで確認します。

## 機能シナリオの設計

利用者の操作では、成功したときと失敗したあとに何が見えるかを決めます。

各シナリオでは、必要な範囲で次を確認する。

- 操作を受け付けたか、最後にどうなったか
- Operationが終わったか、利用者にどのエラーを返すか
- API、CLI、DNS、公開URLから使えるか
- source、runtime、named volumeを残すか消すか
- もう一度実行したときに正しく戻るか
- secretやホスト上のpathを表示しないこと

失敗したときは、機能定義書に書かれた「残すもの」と「消すもの」を確認します。たとえば、sourceの確認に失敗しても古いsourceは残すこと、Dockerの再設定に失敗しても今公開しているアプリは使えること、`purge`ではLWSのDocker resourceだけを消すことです。

決まった秒数だけ待つのではなく、healthcheckやOperationの状態を見て完了を待ちます。

## テスト項目と実装

機能テストのIDは、対応する機能定義書のIDを使います。主なIDは次のとおりです。

| 区分 | ID | 正本 |
|---|---|---|
| fixture基盤 | `TF-V1-xxx` | `scripts/test-fixtures.sh` |
| v1受け入れシナリオ | `FT-V1-xxx` | `qa/suites/**/*.robot` |
| Coreの単体・境界・統合テスト | Goの`Test...`、Shellの対象別テスト | 対象コンポーネントのテスト |

Robotのテスト名には`FT-V1-xxx`を含める。Shellで機能項目を出力する場合は、次の形式を使用する。

```text
TEST_ITEM|<テスト項目ID>|<成功または失敗>|<概要>
```

まだ作っていない受け入れテストには`planned`タグを付けます。作り終えたらタグを外し、品質ゲートで実行します。実装前には、仕様どおりにテストが失敗することを確認します。

## QAの実行

| コマンド | 用途 | 範囲 | 結果 |
|---|---|---|---|
| `mise run qa` | 進み具合の確認 | `live`以外。`planned`を含む | Robot結果を`test/result/robot/`へ作る |
| `mise run qa-current` | 1台で動くQA | `planned`と`isolated`を除外 | `test/result/robot-current/`へ作る |
| `mise run qa-lifecycle` | LWSの起動・停止QA | 一時Compose環境で起動・停止・再構成を実行 | `test/result/robot-lifecycle/`へ作る |
| `mise run qa-live` | 起動済みLWSの受け入れQA | `live`タグだけ | `test/result/robot-live/`へ生成 |
| `mise run qa-docs` | 項目ドキュメント生成 | `qa/suites/` | `docs/generated/`へ生成 |

`qa-live`は、すでに起動しているLWSを使います。`LWS_QA_BASE_URL`、`LWS_QA_BASE_DOMAIN`、repository URLなどを設定して実行します。接続できることもテストします。

`qa-lifecycle`はホストのDockerと80/tcp、53/tcp、53/udpを使います。ほかのサービスとぶつからない専用環境で実行します。インストールQAは、一時Dockerコンテナのrootで実行し、終了後にコンテナを消します。`qa`、`qa-current`、`qa-lifecycle`と実Docker統合テストは、実行前になかったDockerイメージも終了時に削除します。実行前からあるイメージとDocker build cacheは残します。

## 品質ゲート

品質ゲートは`mise run verify`です。普段は変更した場所のテストを実行してから、必要なプロファイルを実行します。

| コマンド | 用途 | 含む検証 |
|---|---|---|
| `mise run verify` または `mise run verify fast` | 普段の開発・通常CI | 静的検査、Core高速テスト、SDK、Dashboard |
| `mise run verify qa` | QAを含めた確認 | fast、Core統合テスト、自己完結QA、隔離ライフサイクルQA、QAドキュメント |
| `mise run verify release` | リリース前の確認 | qa、`.deb`・`.rpm`パッケージ生成 |

通常CIではfastを、LWSのリリースWorkflowではreleaseを実行します。SDKのリリースでは、SDKの`mise` taskを実行します。

品質ゲートは、端末に`VERIFY_ITEM`形式で短い結果を表示します。`PASS`、`FAIL`、`SKIP`と全ログは、`test/result/YYYY-MM-DD-verify-result.md`にまとめます。RobotのHTMLは、このレポートから開けます。`mise run test`だけを実行したときは、結果ファイルを作りません。

## 追加・変更の手順

1. 機能定義書に、前提・操作・成功した結果・失敗したときに残すものを書きます。
2. テストの場所を選びます。利用者の操作はQA、内部の処理はCore、本物のDockerが必要なことは実Docker統合テストです。
3. 機能定義書またはテスト項目書に、テスト項目と実装の対応を書きます。
4. 実装前に、テストが失敗することを確認します。
5. 実装後に、関係するテストと品質ゲートが成功することを確認します。
6. 仕様、実装、テスト項目、MemADRが同じ内容を指していることを確認します。

コンポーネントを追加するときは、そのコンポーネントにlint、test、buildを用意します。そのtaskを`mise`の品質ゲートに追加します。

## 合格基準

機能やリリースを完了とするには、次を満たします。

- 成功する操作と、主な失敗時の動きが確認できている
- 必要なCore・契約・実Docker統合テストが成功している
- 受け入れテストを作った場合、そのRobotテストが成功している
- 実行対象に応じた`mise run verify qa`または`mise run verify release`が成功する
- OpenAPI生成物に意図しない差分がない
- 実行できる環境では、期待した結果をアサーションで確認している
- LWS管理下のDocker resourceだけを使い、テスト後に片付けている

`planned`の項目は、実装が終わったら受け入れテストにして品質ゲートへ追加します。
