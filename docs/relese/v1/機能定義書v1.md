# LabWebSystem 機能定義書 v1

## 1. 文書の位置付け

本書で定義する機能を、LWS正式リリースv1の機能範囲とする。

Backend APIの詳細なschemaは`backend/openapi.yaml`、アプリ定義の詳細は[Infrastructure仕様書](../../Infrastructure仕様書.md)、LWS本体のライフサイクルは既存のCLI契約を正本とする。本書はそれらを利用者の機能とワークフローへまとめたものである。

v1の利用モデルは、信頼できるLAN内で管理者がLWSを運用し、GitHub上のDocker Composeアプリを登録・公開・管理する形とする。認証・認可はv1の対象外である。

## 2. v1の対象範囲

### 2.1 対象

- LWS本体のインストールとライフサイクル管理
- Backend APIによるアプリ登録・設定・実行・削除
- Docker Composeによるアプリ実行
- アプリごとのDNS名とReverse Proxy公開
- SQLiteを正本とする状態管理と派生設定生成
- Operation、SSE、ログ通知、再起動時復旧
- secret保護とLWS所有resource限定操作
- Debian系・RPM系パッケージ配布

### 2.2 対象外

- APIの認証・認可
- WebSocket
- LWSがDHCP設定を自動変更する機能
- KubernetesやDocker Compose以外の実行基盤
- Dashboardの実用管理UI
- 外部アプリ向けTypeScript SDKの本実装
- インターネット公開用のTLS証明書管理

DashboardとSDKは将来の管理クライアント・開発者向け機能として扱い、v1コアの完了条件には含めない。ただし、BackendのOpenAPI契約とアプリmanifest契約はv1で確定する。

## 3. 利用者と状態

### 3.1 利用者

利用者は、LWSホストと同じ信頼できるLANから操作する管理者である。

### 3.2 アプリ状態

アプリの登録状態は`ACTIVE`または`UNREGISTERED`とする。

- `ACTIVE`: アプリ定義が有効で、起動・停止・同期・再構成を行える。
- `UNREGISTERED`: 実行containerとedge networkはないが、source、runtime、設定、named volume、DB記録を保持し、再登録できる。

実行状態、desired state、Operation状態は別に管理する。SQLiteはアプリ定義・望ましい状態・Operationの正本であり、Dockerの実状態は照会して観測する。

## 4. 機能一覧

### F-V1-01 LWSをインストールする

Ubuntu系では`.deb`、AlmaLinux系では`.rpm`をAPTまたはDNFで配置する。インストール時にLWS本体を自動起動しない。対応外OSや必要なパッケージマネージャーがない場合は、環境を変更せず日本語のエラーで終了する。

### F-V1-02 LWS本体を起動・停止・確認・再構成する

許可するCLIコマンドは`start`、`stop`、`status`、`rebuild`、`update`、`down`だけとする。

`start`は初回設定、base domain、installation ID、secret、公開IPv4、DNS・Reverse Proxy設定を準備してLWS本体Composeを起動する。`stop`、`status`、`rebuild`、`update`、`down`は保存データと実行環境の責務を守る。`down --purge`だけが確認後に設定・状態・永続データ・LWS所有volumeを削除する。

### F-V1-03 GitHubアプリを登録する

管理者はGitHub HTTPS URL、ref、subdomainを指定してアプリを登録する。Backendは要求を永続化してOperationを返し、sourceを一時領域へ取得し、manifestとComposeを検証してからアプリを起動する。

公開URLは`<subdomain>.<base-domain>`とする。登録に失敗した場合は、既存アプリがあればsource、実行状態、公開設定を維持する。

### F-V1-04 アプリmanifestとComposeを検証する

アプリrootには`compose.yaml`と`lws.manifest.yaml`を要求する。manifestは`apiVersion: lws/v1`、metadata、公開service、公開portの厳格なschemaに従う。symlink、anchor、alias、duplicate key、未定義キー、外部読込、root外path、bind mount、host port、privileged、Docker socketなどは禁止する。

検証に失敗した入力はGit・Dockerの実行前に拒否する。

### F-V1-05 アプリを公開・停止・再構成する

アプリごとにedge networkを作成し、公開serviceへ`lws-<app-id>` aliasを付ける。Caddyはそのaliasを通じてアプリへ転送する。アプリ間のedge network接続は許可しない。

管理者はアプリのstart、stop、rebuildを実行できる。named volumeは通常の停止・再構成で保持する。

### F-V1-06 アプリ設定とsecretを管理する

Composeから必要な環境変数を抽出し、管理者が値を登録する。secretは暗号化して保存し、API、Operation、ログ、状態表示には値を含めない。`app.env`は起動直前に生成する。

### F-V1-07 アプリをsyncする

新しいrefを一時領域へ取得・検証し、成功時だけsource、runtime、Docker、DNS・Reverse Proxyの公開状態を切り替える。失敗時は旧sourceと旧公開経路を維持する。

### F-V1-08 アプリを登録解除・再登録・完全削除する

登録解除は実行containerとedge networkを削除し、source、runtime、設定、named volume、UNREGISTERED記録を保持する。再登録は保持データを再利用する。完全削除はUNREGISTEREDかつ確認済みの場合だけ許可し、所有確認済みresourceだけを削除する。

### F-V1-09 OperationとSSEで処理を観測する

長時間処理はOperationとして管理する。同一`requestId`は同じOperationを返し、同一アプリの未完了Operationは並列実行しない。Operation状態とコンテナログをSSEで配信し、切断・欠損時はHTTP再取得または再接続で復旧できる。

### F-V1-10 障害後に安全に復旧する

Git、Compose、Docker、Caddy、CoreDNS、DB、ネットワークなどの失敗時はOperationを失敗状態にし、保持すべき旧状態を維持する。Backend再起動時は未完了Operationを`failed`へ整理し、SQLiteを正本としてedge networkと派生設定を再調整する。

### F-V1-11 配布物を更新する

LWSリリースではpackage、`lwsctl`、Compose定義、Backend・Dashboard imageのバージョンを揃える。`lwsctl update`は対応releaseとGHCR imageを更新し、更新前に起動中だった場合だけ再構成・再起動する。停止中のLWSは停止状態を維持する。

## 5. v1の完了条件

- 本書のF-V1-01〜F-V1-11に対応する機能テストがGREENである。
- 正常ワークフローと主要な失敗・再試行ワークフローが検証済みである。
- LWS外のDocker resourceを操作しないことを自動テストで確認している。
- `mise run lint`、`mise run test`、`mise run package`が成功する。
- v1のAPI、manifest、CLI、パッケージ契約が文書と実装で一致する。
