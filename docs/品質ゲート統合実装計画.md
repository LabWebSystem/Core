# 品質ゲート統合実装計画

## 目的

Core、SDK、Dashboard、QAの検証を、それぞれの責務を保ったまま`mise`の品質ゲートへ統合する。GitHub ActionsとリリースWorkflowは品質ゲートを呼び出すだけにし、コンポーネント追加時にWorkflowへ個別のテストコマンドを増やさない。

## 品質ゲート

| task | 目的 | 含む検証 |
|---|---|---|
| `verify` / `verify fast` | 開発・通常CI用の高速検証 | 静的検査、Core高速テスト、SDK、Dashboard |
| `verify qa` | QA前の統合検証 | fast、Core統合テスト、自己完結QA、隔離ライフサイクルQA、QAドキュメント |
| `verify release` | LWSリリース前の検証 | qa、パッケージ生成。digest注入はrelease workflowの責務 |

## 責務

| 対象 | 所有する検証 |
|---|---|
| Core | Go、Shell、fixture、Infrastructureの内部・境界テスト |
| SDK | npmのtestとbuild |
| Dashboard | Docker imageのbuild検証。実装後はDashboard自身のlint、test、buildを追加する |
| QA | 利用者が観測するCLI、API、UI、公開経路をまたぐ受け入れシナリオ |
| 構造検査 | `mise`、Workflow、QAの責務境界 |

QAは`go test`、`npm test`、`scripts/test.sh`を実行して成功扱いにしない。未実装の受け入れシナリオは`planned`として管理し、対応するコンポーネントテストとは別に実環境を用いた検証へ移行する。

## 実装順序

1. Bashによる構造検査を追加し、現状で失敗することを確認する。
2. `mise`に品質ゲートとSDK・Dashboard検証を追加する。
3. CIとLWS・SDKリリースWorkflowを品質ゲート呼び出しへ置換する。
4. QAから内部テストの代理実行を除去し、未実装の受け入れシナリオを`planned`へ戻す。
5. 構造検査、品質ゲート、既存の関連テスト、MemADR検査を実行する。

## 完了条件

- 通常CIは`mise run verify`、LWSリリースは`mise run verify release`を実行する。
- `verify`は端末へ統一した項目要約を出力し、全検証の結果と生ログを`test/result/YYYY-MM-DD-verify-result.md`へ保存する。
- SDKとDashboardが通常CIの品質ゲートに参加する。
- Workflowに`go test`、`npm test`、`npm run build`、`robot`、`scripts/test.sh`を直接書かない。
- `qa/`に内部テストを代理実行するキーワードがない。
- `mise run test architecture`が上記の構造を検査する。
